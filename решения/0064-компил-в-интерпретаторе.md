# 0064. Этап 2: `компил` в интерпретаторе — типы как значения

- Статус: принято
- Версия: v0.180
- Спецификация: §12.2; §12.3; §12.5; §14.3, п. 2

## Решение

Интерпретатор исполняет `компил`-код тем же обходом CST, что и обычный: тип — значение (`тип`), `компил`-параметр — привязка с типом-значением. `структ { … }` и `переч { … }` внутри функции порождают объявление, которое мемоизируется по месту в исходнике и значениям `компил`-параметров функции: `Пара(ц32, стр) == Пара(ц32, стр)`, а `Пара(стр, ц32)` — другой тип. Пропущенные ведущие `компил`-параметры выводятся из аргументов, чей тип записан прямо этим параметром (`а: Т`, `&Т`, `?Т`); остальные пишут явно (§12.5, п. 8). `компил выражение`, `компил если` и `цикл компил` исполняются на месте.

Замыкание запоминает ячейки видимых привязок кадра: захват по умолчанию — ссылкой, `функ[копия]` копирует их при создании. `дин` и `Уник` стираются до ссылки на значение: вызов метода ищет его по типу самого значения.

## Причина

§12.5 делает обобщения обычными функциями времени компиляции, и интерпретатор этапа 2 — тот самый исполнитель `компил` (§14.3). Мемоизация по значениям аргументов — это правило §12.5, п. 3, без неё одинаковые инстанцирования были бы разными типами.

## Отвергнутые варианты

- Мономорфизация до исполнения: дублирует то, что делает `компил`, и нужна только бэкенду (§11).
- Вывод `компил`-параметров унификацией типов: §12.5, п. 8 требует только структурного сопоставления, а полный вывод ждёт проверки типов.
- Копия всех захватов: захват по умолчанию — ссылкой (§12.2), а мутация через замыкание должна быть видна снаружи.

## Плата

`компил` пока исполняется только при запуске: проверка типов не вызывает его и считает тип вроде `Пара(ц32, стр)` неизвестным. Нет `компил_инфо` и бюджета шагов (§12.5, п. 5, 7). Ведущий параметр, тип которого стоит внутри другого типа (`[]Т`, `Пара(Л, П)`), не выводится.
